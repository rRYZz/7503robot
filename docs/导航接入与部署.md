# 定位导航接入与部署（2026-10-10）

定位、地图规划、进退架和树莓派轨迹跟踪已接入本仓库。主框架使用仓库最新的 `NavigateToPoint` 点位接口、`SetBool` 升降接口以及 `ready/fault` 在线接口。实机 mission_robot.yaml 与联合仿真 mission_rack.yaml 的成功流程相同，均含起点扫描和最后 END 扫描；上游通用 mock 的 mission.yaml 仍保留简化流程。

## 项目架构与数据管线

```text
雷达驱动 /scan (LaserScan)
  → robot_navigation/localization.py：四壁匹配，估计位置、航向与速度
  → /odom + TF map→odom→base_link→laser
  → Nav2 global_costmap（只托管地图，不运行 Nav2 速度控制器）
  → navigation.py：点位名→导航自己的 map 坐标→4 连通路径
  → TrackPath action → path_tracker.py（树莓派 ROS 节点）
  → /cmd_vel (Twist) → velocity_json_bridge → base/cmd_vel_json (String.data JSON)
  → 队友的 ESP32 通信→麦轮逆运动学→编码器轮速闭环

mission_manager：START_SCAN/START QR→A/B/C/D→Dock ENTER→升降→DROP_OFF→放下→Dock EXIT→FINAL_SCAN/END QR
Dock ENTER/EXIT → navigation.py + docking.py → 同一个 TrackPath → 同一个 /cmd_vel
```

`NavigateToPoint` 是状态机与导航的边界；主程序只发送 `target_id`。`NavigateToPose` 是导航内部位姿入口，任务层不调用。`TrackPath` 是本包规划器与本包跟踪器之间的执行动作。`navigation/path` 的 Path 话题用于观察，不代替执行动作的完成反馈。

## 框架接口与分工

相对名称见 `src/robot_bringup/config/interfaces.yaml`。实机前缀为 `/team2/robot`，Gazebo 前缀为 `/team2/sim`。

| 接口 | ROS 类型 | 内容与提供者 |
|---|---|---|
| `navigate_to_point` | `mission_interfaces/action/NavigateToPoint` | 主框架发送 `A/B/C/D/DROP_OFF/START_SCAN/FINAL_SCAN`，本包导航返回实际到达并停止后的 success/message |
| `qr/detections` | `std_msgs/msg/String` | 视觉组发布带 image_stamp 的完整 QR JSON，主框架接收；仿真可用测试脚本发布 |
| `docking/execute` | `mission_interfaces/action/Dock` | ENTER/EXIT，本包 navigation_server 提供；实机与联合仿真运行同一代码 |
| `lift/set_up` | `std_srvs/srv/SetBool` | true 升、false 降；升降组实际完成后响应，主框架直接推进 |
| `robot/status` | `std_msgs/msg/String` | 联调组汇总 `{"ready":true,"fault":""}`；健康应保持到正常升降结束，不能把导航 ready=false 暂态作为掉线 |
| `safety/stop` | `std_srvs/srv/Trigger` | 联调组协调导航、Dock、底盘与升降停止/保持，完成后响应 |
| `navigation/stop` | `std_srvs/srv/Trigger` | 本包确认导航/TrackPath 已停止；整机停止协调器调用它，但它不代表其它机构已停止 |
| `navigation/status` | `std_msgs/msg/String` | 本包的 healthy/ready/fault；整机在线汇总依据 healthy，ready 表示当前能否开始运动 |
| `base/feedback` | `std_msgs/msg/String` | 底盘/升降组提供的实测反馈，导航和跟踪内部使用，不改变主框架的简单在线消息 |
| `/scan` | `sensor_msgs/msg/LaserScan` | 雷达组，距离 m、角度 rad、实际采集时间、laser frame |
| `/odom` | `nav_msgs/msg/Odometry` | 本包雷达估计；位置在 odom 场地坐标，twist 在 base_link |
| `/cmd_vel` | `geometry_msgs/msg/Twist` | 普通导航和 Dock 均由本包同一跟踪器发送；底盘组接收并实际执行 |
| `base/cmd_vel_json` | `std_msgs/msg/String` | 本包将 /cmd_vel 转成 linear/angular 六字段 JSON，供 ESP32 通信模块发送 |

导航需要实测停止和携货状态，所以 `base/feedback` 是必要的导航反馈输入；它不由主状态机额外检查，也不能用简单 `robot/status` 代替。建议至少 10 Hz，字段如下，stamp 使用当前测量时间，不能照抄示例时间：

```json
{"schema_version":1,"stamp":{"sec":123,"nanosec":0},
 "modules":{"base":true,"lift":true},"fault":"",
 "stopped":true,"base_motion_stopped":true,"lift_motion_stopped":true,
 "lift_is_up":false,"lift_settled":true,"lift_state_source":"measured"}
```

升降中 `lift_is_up=null,lift_settled=false`；机构到位后才为 true/false。`stopped` 表示实测底盘与机构停止，不是“发过零速度”。测量来源标签只是约定，执行端必须确实有测量。本包不实现编码器、平台传感器和串口接收程序。

## ESP32 接什么数据

实机启动入口自动运行 velocity_json_bridge，将 /cmd_vel 的 Twist 逐条转换成 /team2/robot/base/cmd_vel_json 的 std_msgs/String。底盘组订阅该话题，将 data 中的 JSON 字符串发送给 ESP32。联合仿真同样启动转换节点，输出 /team2/sim/base/cmd_vel_json，便于核对；Gazebo 执行端仍订阅原 Twist，联合仿真不代表串口/ESP32 链路已验证。

```json
{"linear":{"x":0.10,"y":0.0,"z":0.0},"angular":{"x":0.0,"y":0.0,"z":0.0}}
```

这就是 String.data 中的完整 JSON，无外层 data 字段、无额外坐标系变换。linear.x 是车头方向速度，linear.y 是左向速度，单位 m/s；angular.z 是逆时针转速，单位 rad/s，其余分量固定为零。默认输入20 Hz，正常命令到达后立即转换一次，不定时重发缓存的非零速度。ESP32 将这三个速度转换成四轮目标转速，用编码器 PID 跟踪，负责限幅和急停。

启动后尚无指令、输入断流超过 tracking_command_timeout_sec（默认0.3秒）、出现非有限值/不支持轴/超限速度或节点正常退出时，转换节点输出全零速度。断流检测使用单调墙钟，仿真暂停也有效。零速心跳按 tracking_frequency（默认20 Hz）发送。Twist 本身不含采集时间戳，此处的超时按本机收到消息的时间计算；转换进程崩溃、通信断开等情况仍必须由 ESP32 自己的命令看门狗停车，收到零速也不能当作实测已经停止。

JSON 出口配置在 navigation_robot.yaml 的 cmd_vel_json_topic: base/cmd_vel_json，名称由启动命名空间补全。QoS 为 reliable、volatile、深度1，不使用历史缓存触发新运动。实机启动后可由操作者检查：

```bash
export ROS_DOMAIN_ID=42
ros2 topic echo /team2/robot/base/cmd_vel_json --field data
```

联合仿真使用 ROS_DOMAIN_ID=0 和 /team2/sim/base/cmd_vel_json。两个启动入口都已包含转换节点，无需再起一份。

ROS→JSON 转换已由本包完成，实际串口/USB 发送程序和 ESP32 固件由底盘组实现。使用串口时可约定 UTF-8 编码、每条 JSON 后追加一个换行符（\n），ESP32 按行解析；发送程序和固件需一致采用该约定，当前转换节点不访问串口设备。micro-ROS 可直接订阅原 Twist 或这个 String 话题，底盘只选择一个控制来源。速度指令不能直接当 PWM。Path 不发给 ESP32；轨迹位置误差由树莓派跟踪器根据新雷达位姿修正。平移仅沿场地轴，不斜走；空载扫描允许原地旋转，载货禁止旋转。

独立慢速底盘测试与导航使用同样的 `/cmd_vel`、Twist、QoS 和控制周期：

```bash
bash scripts/底盘测试脚本.sh
```

由操作者确认场地后运行。测试脚本不确认实物已经停稳；测试时不能同时运行另一个速度发布者。

若底盘测试也要走 JSON 接口，只启动转换器和底盘通信程序，另开终端运行底盘测试脚本，不启动整个导航链。先 source ROS/install 并 export ROS_DOMAIN_ID=42，然后运行：

```bash
ros2 run robot_navigation velocity_json_bridge --ros-args -r __ns:=/team2/robot
```

导航和测试脚本都会经过同一份转换代码、同一 JSON 话题。转换节点不伪造 base/feedback，底盘/平台实测反馈格式仍按前面的约定回传。

## 下载、构建与实机启动

源码只需一个项目目录，可放在任意路径。首次在 Ubuntu 24.04/ROS 2 Jazzy 环境克隆：

```bash
git clone https://github.com/sxttrt/7503robot.git ~/7503robot_ws
cd ~/7503robot_ws
source /opt/ros/jazzy/setup.bash
rosdep install --from-paths src/mission_interfaces src/mission_manager src/robot_navigation src/robot_bringup --ignore-src -r -y
bash scripts/build.sh --robot
bash scripts/run_robot.sh
```

`run_robot.sh` 默认启动本包定位、costmap、导航（含 Dock）和跟踪，等待雷达与实测反馈；不启动 Gazebo、QR、ESP32 通信、升降或整机健康/停止。校准标记默认 false，导航点位、架口几何和真实 QR 默认 null，未填写时不会放行运动。

实机准备好后填写 `navigation_robot.yaml`、`navigation_points_robot.yaml` 与 `targets_robot.yaml`，各组同用通信域 42，再从同一入口加上主框架：

```bash
bash scripts/run_robot.sh start_mission:=true
```

另一终端 source ROS 和 install 后人工启用：

```bash
export ROS_DOMAIN_ID=42
ros2 service call /team2/robot/mission/arm std_srvs/srv/Trigger '{}'
```

实机与联合仿真都发送 START_SCAN/FINAL_SCAN，实机从自己的实测点位读取坐标，禁止使用 simulation_only=true 的仿真点位。主框架三个配置不包含导航坐标。相同流程不等于相同配置：实机限时 180 秒、QR 连续三帧且不允许超时放行；联合仿真可用脚本单帧触发和超时推进。

## 进退架如何接实物

此部分属于我们的导航：框架在识别 QR 后调用 Dock ENTER，导航先在架外对齐 y，再沿场地 -x 到架中心，雷达位置与实测速度满足停止条件才返回 ready_to_lift。升降组此后执行 lift/set_up；搬运到投放点并完成放下后，框架调用 Dock EXIT，导航从该投放点沿 +x 退出，确认整车脱离并停稳后才前往下一货架。举起后直接规划送货，不额外先退出一截。

导航负责人在 navigation_points_robot.yaml 的 docking.A/B/C/D 填写以下实测几何（米），示例结构仅用于说明，数值必须实测：

```yaml
docking:
  A:
    bounds: [1.051, 1.221, 0.351, 0.729]
    leg_thickness: 0.030
    exit_distance: 0.450
    max_entry_distance: 0.600
```

bounds 为货架外矩形，架口在 +x 侧，两条腿带位于 y 下沿/上沿；空车尺寸、偏航包络、5 cm 间距和跟踪余量必须能通过净宽。ENTER 使用原货架几何中心；EXIT 将该几何平移到该架投放点。进入距离受上限约束、退出必须完全脱离、全路径不得越过场地边界。当前实现面向这种矩形架口几何，其它结构应先修改并验证几何模型。

架口窄段按授权允许不使用 costmap 占据判定，以免自身架腿膨胀挡住入口；仍由雷达闭环跟踪，持续检查几何走廊、航向、测量新鲜度和平台已放下状态。此模式不检测走廊内新增异物，因此应保证已标定架口及退架通道清空。其它路径仍使用正常地图避障。

Dock 不驱动升降、不检查私有二维码缓存；expected_qr 来自状态机已确认的完整 QR，动作按当前货架/状态/请求编号关联。ENTER 成功只表示导航已到已标定托举位置并停稳，机构组仍负责机械接触、行程、载荷和升降到位测量。整机停止先调用 navigation/stop（同时取消导航、Dock 和 TrackPath），再停止/保持升降等机构，完成后响应 safety/stop。

更新代码用 `git pull --ff-only` 后重新构建。Git 不上传 build/install/log；树莓派必须自行构建，不能使用电脑的 WSL 构建结果。树莓派运行 ROS 软件属于部署；ESP32 固件另行烧录。

## Gazebo 联合验证与现有仿真流程

安装 Gazebo Harmonic、ros_gz_bridge 和导航依赖后，由操作者执行：

```bash
cd ~/7503robot_ws
bash scripts/build.sh
bash scripts/run_rack_hybrid.sh
```

联合验证用实际定位、导航、进退架和跟踪代码接收 Gazebo 雷达，Gazebo 执行 `/cmd_vel` 并模拟升降机构。hybrid_execution 不注册 Dock，只在真实 Dock 完成后选择模拟货架并执行升降。真值只用于执行反馈和误差评估，不进入定位器。普通历史货架仿真入口为 `bash scripts/run_rack_sim.sh`；要验证实机导航及进退架使用 run_rack_hybrid.sh。上游接口 mock 为 `ros2 launch robot_bringup simulation.launch.py`，它使用域 62；货架 Gazebo 使用域 0，两者用途不同。

货架流程：NAV_START→起点前方左转30°→WAIT_START→回正后前往 A→WAIT_RACK_QR→进架→抬升→DROP_OFF→自动放下→退出→B/C/D；四架完成后 NAV_FINAL→终点前方左转30°→WAIT_FINAL_QR→实际停车→结束运行。落点按 scene.py 从左到右、从里到外；主框架每次仅发 DROP_OFF，导航用当前 NAV_END 的货架上下文选择落点，不能用请求次数猜货物。

其它终端统一设置域 0 并 source ROS/install：

```bash
source /opt/ros/jazzy/setup.bash
source install/setup.bash
export ROS_DOMAIN_ID=0
export RMW_IMPLEMENTATION=rmw_fastrtps_cpp
export ROS_AUTOMATIC_DISCOVERY_RANGE=SUBNET
ros2 topic echo /team2/sim/mission/status
```

只在相应 QR 等待状态发布：

```bash
python3 scripts/publish_qr_result.py START
python3 scripts/publish_qr_result.py RACKA_XXXX   # 后续 B/C/D 按当前等待货架发布
python3 scripts/publish_qr_result.py END
```

货架仿真 QR 等待默认 15 秒，超时可自动推进；实机禁止此选项。导航、进退架、升降和最终停止必须实际完成，不能用超时伪造成功。取消旧 `/rack/next` 的任务等待。停止：`bash scripts/stop_rack_sim.sh`。

地图允许场地内未知格通行，但仍检查已知障碍、整个车辆/载货包络、5 cm 间距、跟踪余量和场地边界。Nav2 保留原始未知格以供诊断；地图不是无限平面。

## 验证与实际限制

本次合并只运行离线测试和构建，未启动 Gazebo、ROS 运动节点或真实硬件。接口兼容不代表树莓派性能或实物搬运已经验证。当前定位依赖已知矩形四壁、正确初值和足够雷达回波；真实驱动若仅输出 PointCloud2，需要有效扫描平面转换。

2026-10-26 验证：加入 Twist→JSON 转换和两个启动入口后，4个实机包构建成功，557项框架/导航离线测试通过。覆盖 JSON 字段与方向、非有限值/超限速度拒绝、断流归零、不重发缓存非零命令、退出时拒绝运动指令、配置向后兼容和启动文件接入。此次未启动转换节点、Gazebo 或串口设备，实时传输和 ESP32 固件仍需操作者联调。

先单测雷达与 TF、底盘慢速速度跟踪、升降完成反馈、Dock 和停止，再联调整机。状态机记录在 runtime_logs，联合评估含期望速度、雷达位姿、真值和采样时间；规划失败保存地图快照。问题排查应对齐同一时刻的点位请求、Path、cmd_vel、雷达位置和执行反馈，不能用“命令发出了”证明底盘已经运动。
